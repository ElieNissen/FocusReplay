# Deploy your own FocusReplay instance

## Audit result

The original `web/` source was **not a complete independent deployment procedure**: its default build generated a Sites Worker with placeholder D1/R2 identifiers, its documentation assumed Sites would provision resources, and account setup depended on an operator-generated publishing key. No real secrets were committed, but a fresh clone lacked an end-to-end onboarding and runtime path.

The standalone target removes these runtime dependencies. It builds the same replay interface as a static client, runs the same access-control API on Node 24, uses SQLite and a private image directory, and generates its own root secret on first boot. It never calls Codex, OpenAI, Sites, or the original hosted instance. The Worker/Sites target remains an optional alternative.

## Docker installation

Requirements: a server with Docker Compose, a domain pointing at that server, and inbound TCP ports 80 and 443. Run from a fresh clone:

```sh
git clone https://github.com/ElieNissen/FocusReplay.git
cd FocusReplay/web
printf 'DOMAIN=focus.example.com\n' > .env
docker compose up --build -d
docker compose logs app
```

Replace `focus.example.com` with your domain. Caddy obtains and renews HTTPS certificates; the app has no publicly published port and is reachable through the proxy. DNS/firewall configuration is the operator's responsibility. See [Caddy HTTPS documentation](https://caddyserver.com/docs/automatic-https).

The app log contains an **invitation code**, not the root server key. In the Windows application, open **Profil → Créer mon compte**, enter your server address, choose an identifier and account password, and enter that invitation code. Set a *separate viewer password* and activate sharing. Friends create their own accounts the same way. A connection JSON file is no longer needed. Give visitors only a profile URL and its viewer password; give the invitation code only to people allowed to create accounts.

Account credentials control publishing. A viewer password cannot sign in to an owner account. Publishing credentials are transferred directly to Electron's main process over HTTPS and encrypted with Windows account protection; renderer state never contains them. The desktop does not save the account password. Invitations can be rotated by setting `REGISTRATION_CODE` in the app container environment, then recreating the app container. Rotation does not revoke existing accounts.

## Local verification without Docker

To offer normal signup without invitation codes, set `OPEN_REGISTRATION=true` and optionally `MAX_ACCOUNTS=100` in the application environment (for Docker, add these under `app.environment` in Compose). The UI detects this mode on the website. Desktop users expand **Serveur personnalisé** for an independent instance. Signup requires an email, a public handle and a password; existing handle-only accounts still work. Email verification/delivery and password recovery are not implemented. Keep this an early beta until those account-management features are operational. The rate limits and account cap bound initial exposure; they do not replace ongoing abuse monitoring.

Node 24.14 or newer is required; no external database or cloud account is needed:

```sh
cd web
npm ci
npm run build:standalone
npm run test:standalone
npm run start:standalone
```

Open `http://localhost:8787`. HTTP is allowed only for loopback addresses during local testing. For an exposed deployment, set `PUBLIC_ORIGIN=https://your-domain` and place the server behind HTTPS. `HOST` defaults to `127.0.0.1`; Docker sets `0.0.0.0` on its private network. Do not expose port 8787 publicly when `TRUST_PROXY=1`: that mode trusts only the supplied reverse proxy for client addresses.

The standard `npm run build` still builds the optional Worker target. `build:standalone` never imports the Sites Vite plugin or its mock local identity. Dependency downloads happen during installation/build; none are required by the standalone runtime image.

## Persistence, backups and removal

The `replay_data` volume holds the SQLite database, images and `server-secret`. The root key is generated by that instance, never supplied by Codex. Keep the volume private. Restarting or rebuilding containers preserves accounts and keys. **Never run `docker compose down -v` unless you intend to delete the data.**

For a consistent backup, stop the app container, back up the complete `replay_data` volume including the database, WAL files if present, images and secret, then restart it. A database-only backup is insufficient: losing the root secret invalidates existing publishing credentials and viewer sessions. Restore to an isolated environment before changing production DNS. No automated backup service is included.

Images expire after 90 days; the standalone server removes expired manifest images on startup and hourly, independently of desktop connections. The app keeps up to 800 reduced images per profile (40 MB maximum for active images), with fewer samples in older age ranges. Metadata, backups, filesystem overhead and temporary writes are separate. Daily totals outlive images. This is not an end-to-end encrypted service: the server operator can access data and must protect the host and backups.

## What is verified and what is still an operator responsibility

Automated tests start an independent datastore, generate fresh secrets, register/login, restart, separate owner/viewer passwords, deny unauthorized media, reject object-path traversal and clean expired images. The desktop integration test starts the complete standalone HTTP server, creates an account through the UI, configures viewing, publishes an empty fictional session state and removes it without a file or hosted service. CI also builds and boots the Docker image from the repository.

A real public-domain certificate, DNS, provider firewall and production backup/restore must be verified by the deploying operator. The current standalone deployment is a single-server installation for an invited group, not a horizontally replicated service. Account-password reset, individual device revocation and invitation administration are not yet exposed in the UI; keep registration limited until those controls ship. Existing legacy profiles retain their encrypted connection, but cannot be claimed by a new account registration: choose a new account identifier until a verified migration flow is available.
